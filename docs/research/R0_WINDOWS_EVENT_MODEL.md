## Purpose and evidence labels

This document defines the Windows observation boundary for R0. It covers only
enumeration, event receipt, snapshotting, logging, and geometry calculation. It
does not authorize window control, polling, input hooks, DLL injection, Snap,
Glue, zones, or grouping.

Claims below use these labels:

- **DOCUMENTED** — stated by Microsoft in the linked Windows documentation.
- **R0 RECOMMENDATION** — a PaneBind design choice derived from documented
  contracts. It is not presented as Windows behavior.
- **NOT TESTED** — an empirical question that still requires a focused observer
  run. No manual observations are claimed in this document.

All technical sources used here are official Microsoft documentation. No code
was copied or adapted from an external implementation.

## Baseline decisions

R0 should use:

1. `EnumWindows` for an initial, non-atomic census of top-level desktop-app
   windows;
2. two `SetWinEventHook` registrations, both
   `WINEVENT_OUTOFCONTEXT | WINEVENT_SKIPOWNPROCESS`;
3. only `EVENT_SYSTEM_MOVESIZESTART`,
   `EVENT_OBJECT_LOCATIONCHANGE`, and `EVENT_SYSTEM_MOVESIZEEND`;
4. explicit top-level/window-object filtering at the Windows adapter boundary;
5. separate positioning and visible-frame rectangles;
6. a Per-Monitor V2 observer process; and
7. best-effort snapshots in which unavailable fields remain unavailable rather
   than receiving fabricated defaults.

These choices remain observation-only.

## Enumeration contract

### What `EnumWindows` guarantees

**DOCUMENTED.** [`EnumWindows`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-enumwindows)
passes each top-level window on the screen to a callback until enumeration
finishes or the callback returns `FALSE`. It does not normally enumerate child
windows, although Microsoft documents an exception for a few system-owned
top-level windows that carry `WS_CHILD`. Microsoft also documents it as safer
than walking a `GetWindow` chain, which can loop or encounter destroyed
handles. On Windows 8 and later, its documented scope is top-level windows of
desktop applications.

If the callback intentionally returns `FALSE`, it should set a last-error value
so the caller can distinguish intentional termination from API failure. A
successful callback should continue by returning `TRUE`.

### R0 census semantics

**R0 RECOMMENDATION.** Treat enumeration as a census, not an atomic snapshot.
Install both event hooks first, then run `EnumWindows`, while retaining queued
events. Mark records by origin (`initial_census` or `winevent`) rather than
pretending that census rows and event rows came from one transaction. A window
can be created, destroyed, or mutate between any two calls.

Every enumerated handle should be passed through the same structural and policy
filter described below. Do not enumerate by repeatedly calling `GetWindow`.
Do not infer that an empty title means an irrelevant window.

**NOT TESTED.** Verify how current packaged applications, hosted application
windows, and Windows shell surfaces appear in `EnumWindows` on the supported
Windows versions. The documented Windows 8+ “desktop applications” limitation
is a coverage risk and must not be silently generalized to every app model.

## WinEvent hook contract and lifetime

### Registration

**DOCUMENTED.** [`SetWinEventHook`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwineventhook)
registers an inclusive range from `eventMin` through `eventMax`. With process
and thread IDs both zero, the hook receives matching events from all processes
and threads on the current desktop. With `WINEVENT_OUTOFCONTEXT`, the callback
is not mapped into event-generating processes; events cross the process
boundary through a queue and are asynchronous, but Microsoft guarantees
sequential order. `WINEVENT_SKIPOWNPROCESS` prevents that hook instance from
receiving events generated by the observer's own process.

For an out-of-context callback, `hmodWinEventProc` is `NULL`. A zero hook handle
means registration failed. The returned nonzero handle must be retained for
`UnhookWinEvent`.

### Why there are two hooks

**R0 RECOMMENDATION.** Use these exact registrations on one hook-owning thread:

| Hook | Inclusive range | Purpose |
| --- | --- | --- |
| System move/size | `EVENT_SYSTEM_MOVESIZESTART` through `EVENT_SYSTEM_MOVESIZEEND` | The two constants are contiguous (`0x000A` and `0x000B`). |
| Geometry | `EVENT_OBJECT_LOCATIONCHANGE` through `EVENT_OBJECT_LOCATIONCHANGE` | Exact single object event (`0x800B`). |

A single range from `0x000A` through `0x800B` would subscribe to many unrelated
events. Three single-event hooks would also be valid, but two handles express
the approved minimal set without widening it. If either registration fails,
startup should report the observer as incomplete rather than claiming full R0
coverage.

### Threading, message loop, reentrancy, and shutdown

**DOCUMENTED.** The thread that calls `SetWinEventHook` must have a message loop.
Out-of-context events are delivered on that same installing thread.
[`SetWinEventHook`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwineventhook)
also warns that a hook can reenter while processing an earlier event. Microsoft
specifically notes that APIs which check the owning thread's message queue, and
cross-process accessibility/COM calls, can permit reentrancy; see
[`Guarding Against Reentrancy in Hook Functions`](https://learn.microsoft.com/en-us/windows/win32/winauto/guarding-against-reentrancy-in-hook-functions).

**R0 RECOMMENDATION.** The callback should perform only bounded work:

1. copy the raw callback tuple;
2. assign an observer sequence number and receive timestamp;
3. apply the object/child/root checks below;
4. capture lightweight, non-controlling window facts needed to correlate the
   event as close to delivery time as practical; and
5. enqueue the record for serialization and optional metadata enrichment.

Do not call accessibility interfaces, show UI, run nested message loops, or send
arbitrary messages to target windows from the hook callback. Protect sequence
assignment and callback state against reentrancy. If a bounded queue overflows,
emit an explicit loss/overflow diagnostic with a count; never silently claim a
complete trace. Snapshot capture time must be distinct from native event time
because an out-of-context event is asynchronous.

**DOCUMENTED.** [`UnhookWinEvent`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-unhookwinevent)
fails when called from a different thread than the corresponding
`SetWinEventHook`. If the client thread exits, Windows automatically unhooks,
but orderly teardown should not depend on that fallback. After
`UnhookWinEvent` returns successfully, its callback no longer receives event
notifications.

**R0 RECOMMENDATION.** Own both hook handles, the callback target, the queue,
and the message loop as one lifetime unit. On orderly shutdown, unhook both
handles on the installing thread, check each result, drain or explicitly mark
discarded queued records, and only then destroy callback state and exit the
thread.

## Native event meanings and normalized mapping

Microsoft's [`Event Constants`](https://learn.microsoft.com/en-us/windows/win32/winauto/event-constants)
document the following:

| Native event | Documented meaning | R0 normalized type |
| --- | --- | --- |
| `EVENT_SYSTEM_MOVESIZESTART` (`0x000A`) | A window is being moved or resized; sent by the system, not servers. | `MoveResizeStarted` |
| `EVENT_OBJECT_LOCATIONCHANGE` (`0x800B`) | An object changed location, shape, or size. Windows generates it for caret and window objects; applications can also generate it for accessible objects. | `GeometryChanged` after filtering |
| `EVENT_SYSTEM_MOVESIZEEND` (`0x000B`) | Movement or resizing of a window finished; sent by the system, not servers. | `MoveResizeEnded` |

For `EVENT_OBJECT_LOCATIONCHANGE`, Microsoft explains that a top-level object
change does not imply a corresponding event for all of its menu, title-bar,
scroll-bar, or other children. It also notes that explicitly resized child
windows can generate their own events. Therefore this event is not intrinsically
“top-level window geometry” until the callback identifiers and HWND ancestry
are filtered.

[`WINEVENTPROC`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nc-winuser-wineventproc)
defines the raw tuple: hook handle, event ID, `HWND`, object ID, child ID, event
thread ID, and event-generation time in milliseconds. `HWND` may be null for
events with no associated window. `idChild == CHILDID_SELF` means the event was
triggered by the object itself. [`OBJID_WINDOW`](https://learn.microsoft.com/en-us/windows/win32/winauto/object-identifiers)
means the window itself rather than one of its child objects.

### Mapping rules

**R0 RECOMMENDATION.** Map accepted native events one-for-one. Do not synthesize
starts or ends, assume balanced pairs, or turn a location event into a
minimize/restore/activation/close event. The selected constants do not
distinguish movement from resizing. A calculation may later compare two valid
rectangles and label the delta “position only,” “size only,” or “both,” but that
is derived geometry, not a stronger native event claim.

The platform-neutral R0 type set remains exactly:

```text
MoveResizeStarted
GeometryChanged
MoveResizeEnded
```

Keep these raw facts in Windows/log metadata rather than exposing Win32 types
to `src/core/`:

- native event ID;
- native object and child IDs;
- event-generating thread ID;
- zero-extended native event-time milliseconds;
- adapter receive and snapshot timestamps; and
- acceptance or rejection disposition.

The callback's documented event time and the observer's wall-clock time are not
interchangeable. The native millisecond value should not be treated as a wall
clock or a durable global causal clock without further evidence.

### Suggested stable record envelope

**R0 RECOMMENDATION.** Machine-readable output should version its schema and
separate raw receipt from snapshot quality. At minimum, an event record should
carry:

```text
schema_version
record_kind                 # event, census_snapshot, diagnostic
observer_sequence
native_event
normalized_event            # absent for rejected native events
native_window_id
pid                         # when captured successfully
native_object_id
native_child_id
native_event_time_ms
received_at
snapshot_captured_at
disposition                 # accepted or a named rejection reason
snapshot
field_errors[]              # api, field, error domain/code
```

An ephemeral HWND value can be formatted as an opaque hexadecimal adapter ID,
but it is not persistent identity. Associate it with PID and an observer-local
generation/first-seen value if records must survive handle reuse. Never place
`HWND`, `DWORD`, `RECT`, or Windows event constants in core types.

## Structural filtering

### Callback object and child filtering

**R0 RECOMMENDATION.** Apply event-specific structural checks:

- For `EVENT_OBJECT_LOCATIONCHANGE`, accept only a non-null HWND with
  `idObject == OBJID_WINDOW`, `idChild == CHILDID_SELF`, and
  `GetAncestor(hwnd, GA_ROOT) == hwnd`.
- For the two system move/size events, require a non-null, currently queryable
  root HWND. Preserve `idObject` and `idChild` in diagnostics, but do not make
  undocumented values a hard filter until R0 observation confirms them. The
  Microsoft event rows identify a window but do not specify the two identifier
  values for these constants.
- Reject a child HWND whose root differs from itself. `GA_ROOT` is documented as
  walking the parent chain to the root by
  [`GetAncestor`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getancestor).
- Reject the observer's PID defensively in both census and event paths.
  `WINEVENT_SKIPOWNPROCESS` covers hook delivery, but it does not filter the
  independent `EnumWindows` census.

This is intentionally stricter for the object event because it can represent a
caret, child HWND, or application-defined accessible object.

### Invalid-handle race

**DOCUMENTED.** [`IsWindow`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-iswindow)
only says that a handle identifies an existing window at the instant of the
call. Microsoft explicitly warns against relying on it for another process's
window: the window can be destroyed immediately afterward and window handles
are recycled.

**R0 RECOMMENDATION.** `IsWindow` may be a cheap rejection hint, but it is not a
lifetime lock. Treat every subsequent API as independently fallible. Capture
PID early with
[`GetWindowThreadProcessId`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getwindowthreadprocessid),
using initialized output storage (`DWORD pid = 0`). Accept the PID only when
the returned thread ID is nonzero; on failure the API does not promise to
replace the output value. Repeat the same initialized thread-ID/PID check after
deferred enrichment. If either call fails or the PID changed, mark the snapshot
stale/identity-mismatch rather than attaching metadata from a recycled handle.

## Window relevance policy

Windows exposes facts; “user-relevant window” is a PaneBind policy. R0 should
keep those separate.

| Fact | Documented semantics | R0 observation policy |
| --- | --- | --- |
| Visibility | [`IsWindowVisible`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-iswindowvisible) tests `WS_VISIBLE` on the window and its parent chain. It can be true even when the window is completely obscured. | Reject from the default candidate stream when false. Record `not_visible` as the reason. Never call true “actually visible” or “unoccluded.” |
| Cloaking | `DwmGetWindowAttribute(DWMWA_CLOAKED)` returns a bit mask for app, shell, or inherited cloaking; a cloaked window still exists but is hidden from the user. See [`DWMWINDOWATTRIBUTE`](https://learn.microsoft.com/en-us/windows/win32/api/dwmapi/ne-dwmapi-dwmwindowattribute). | Reject nonzero masks from the default candidate stream. Preserve the raw mask and distinguish an API failure from `0` (not cloaked). |
| Tool-window style | [`WS_EX_TOOLWINDOW`](https://learn.microsoft.com/en-us/windows/win32/winmsg/extended-window-styles) denotes an intended floating toolbar and normally omits it from the taskbar and Alt+Tab. `WS_EX_APPWINDOW` forces a visible top-level window onto the taskbar. | Reject `WS_EX_TOOLWINDOW` by default unless `WS_EX_APPWINDOW` is also present. This is an R0 heuristic, not a permanent product blacklist. Log the style bits and reason. |
| Minimized | [`IsIconic`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-isiconic) reports minimized state. | Keep and label minimized windows in census/event evidence, but mark current visible geometry as ineligible for adjacency conclusions. Do not equate minimized with hidden style. |
| Maximized | [`IsZoomed`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-iszoomed) reports maximized state. | Keep and label. It remains a valid observation target. |
| Empty title | `GetWindowTextW` can return an empty string for no caption, no text, an empty caption, or an invalid handle. | Never use title emptiness alone as an exclusion rule. |

Retrieve style bits with
[`GetWindowLongPtrW`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getwindowlongptrw)
using `GWL_STYLE` and `GWL_EXSTYLE`. A zero return can be a valid value, so clear
and inspect last error where ambiguity matters.

Use two named outcomes:

- `observed_snapshot`: structurally valid enough to preserve as evidence; and
- `default_candidate`: passes the visibility, cloaking, and tool-window policy.

This permits diagnostic census output to retain rejection facts without
feeding rejected targets into normalized geometry events. The R0 policy must
not be reused later as a Snap/Glue eligibility decision without a new research
gate.

## Window snapshot semantics

### Best-effort and non-atomic

**R0 RECOMMENDATION.** A `WindowsWindowSnapshot` is a best-effort collection of
facts captured over an interval. It is not an OS transaction. Store a status
per optional field or a structured `field_errors` list. Only PID/native handle
correlation and the structural checks are required to accept identity; process
path, title, visible bounds, cloak state, or monitor metadata can be unavailable
without inventing a value.

Recommended Windows snapshot facts are:

| Fact | API and interpretation |
| --- | --- |
| Native window ID, PID, event thread | Raw `HWND` stays in the Windows adapter; PID comes from `GetWindowThreadProcessId`. |
| Executable path/name | Best effort via the minimum-access process query described below. A basename may be derived only when a path is available. |
| Title | [`GetWindowTextW`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getwindowtextw) retrieves another process's top-level caption without requiring control-text retrieval. It cannot retrieve another application's control text; R0 does not need to send `WM_GETTEXT`. |
| Class | [`GetClassNameW`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getclassnamew). Treat truncation/failure explicitly. |
| Style facts | `GWL_STYLE`, `GWL_EXSTYLE`, derived `tool_window` and `app_window` flags. |
| Visibility/state | `IsWindowVisible`, cloak mask, `IsIconic`, and `IsZoomed`. The three Boolean user32 queries do not expose a documented error channel distinct from false; stale/unknown status comes from the bracketing HWND/PID identity checks. Cloak retrieval has independent HRESULT availability. |
| Positioning bounds | Successful `GetWindowRect`, with its coordinate-space label. |
| Visible frame bounds | Successful `DwmGetWindowAttribute(DWMWA_EXTENDED_FRAME_BOUNDS)` only; no silent substitution in the native snapshot. |
| Window DPI/awareness | `GetDpiForWindow`; optional window awareness from `GetWindowDpiAwarenessContext` when interpreting the value. |
| Monitor and work area | `MonitorFromWindow`, then successful `GetMonitorInfoW`; monitor ID remains adapter metadata. |

The normalized snapshot may choose a documented fallback for a field needed by
core—for example, absent visible bounds remain `optional`, not a duplicate of
positioning bounds. Preserve source and availability so later analysis can tell
which rectangle was actually measured.

### Safe process image query

**DOCUMENTED.**
[`QueryFullProcessImageNameW`](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-queryfullprocessimagenamew)
accepts a process handle opened with `PROCESS_QUERY_INFORMATION` or the narrower
`PROCESS_QUERY_LIMITED_INFORMATION`. With flags `0` it returns a Win32-format
path. Its size parameter is buffer capacity in characters on input and the
written count excluding the null terminator on success.

[`OpenProcess`](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-openprocess)
checks requested access against the process security descriptor and documents
expected failures for certain system processes. Its returned handle must be
closed with
[`CloseHandle`](https://learn.microsoft.com/en-us/windows/win32/api/handleapi/nf-handleapi-closehandle).

**R0 RECOMMENDATION.**

1. capture PID from the HWND;
2. call `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION, FALSE, pid)`;
3. call the Unicode image-name API with flags `0` and a bounded, growable
   character buffer;
4. close the handle through RAII on every path;
5. record the Win32 error and leave path/name unavailable on failure; and
6. do not enable `SeDebugPrivilege`, request `PROCESS_ALL_ACCESS`, read process
   memory, or make path availability an observation-eligibility condition.

Processes can exit during the query, and security can deny access. Either is an
expected metadata failure, not permission to elevate the observer. Process
paths can reveal user or installation details, so logs should make path output
an explicit diagnostic field and support redaction in any shared report.

## Geometry model

### Positioning bounds versus visible frame bounds

**DOCUMENTED.** [`GetWindowRect`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getwindowrect)
returns a screen-coordinate bounding rectangle with exclusive right and bottom
edges. It is DPI-virtualized and, on Windows Vista and later, may include
invisible resize borders. Microsoft directs callers to
`DwmGetWindowAttribute(DWMWA_EXTENDED_FRAME_BOUNDS)` for visible bounds that
exclude those invisible resize borders, and notes that the DWM bounds are not
adjusted for DPI.

[`DwmGetWindowAttribute`](https://learn.microsoft.com/en-us/windows/win32/api/dwmapi/nf-dwmapi-dwmgetwindowattribute)
returns `S_OK` on success and an `HRESULT` on failure. The
[`DWMWA_EXTENDED_FRAME_BOUNDS`](https://learn.microsoft.com/en-us/windows/win32/api/dwmapi/ne-dwmapi-dwmwindowattribute)
attribute yields a `RECT` in screen space.

**R0 RECOMMENDATION.** Name the two facts precisely:

- `positioning_bounds`: the rectangle returned by `GetWindowRect`; and
- `visible_frame_bounds`: the rectangle returned by DWM, optional on failure.

Do not call them equal, merge them, or compute adjacency across different
coordinate spaces. Preserve exclusive-edge rectangle semantics when converting
to core `Rect`. Negative virtual-screen coordinates are valid.

These names describe measurement sources; R0 does not use them to position any
window. Which rectangle is appropriate for future user-visible adjacency or
native operations remains a later, evidence-driven decision.

## DPI and monitor model

### Per-Monitor V2 process baseline

**DOCUMENTED.** Microsoft recommends setting default process DPI awareness in
the application manifest rather than through an API. The
[`dpiAwareness` manifest guidance](https://learn.microsoft.com/en-us/windows/win32/hidpi/setting-the-default-dpi-awareness-for-a-process)
uses `PerMonitorV2`; the mode became available in Windows 10 version 1703. Its
documented behaviors include per-top-level-window DPI handling and automatic
non-client/menu/dialog improvements. See
[`DPI_AWARENESS_CONTEXT_PER_MONITOR_AWARE_V2`](https://learn.microsoft.com/en-us/windows/win32/hidpi/dpi-awareness-context).

**R0 RECOMMENDATION.** Declare `PerMonitorV2` in the observer executable's
manifest and treat Windows 10 version 1703 as the minimum for this exact
baseline unless project policy explicitly defines a fallback. Do not call
[`SetProcessDpiAwarenessContext`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setprocessdpiawarenesscontext)
as a redundant second mechanism: Microsoft documents `ERROR_ACCESS_DENIED`
when process awareness has already been set, including by the manifest.

At startup, record a diagnostic verification of the hook/census thread's DPI
context.
[`GetThreadDpiAwarenessContext`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getthreaddpiawarenesscontext)
returns the current thread context (or the process default if no thread
override exists), and
[`AreDpiAwarenessContextsEqual`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-aredpiawarenesscontextsequal)
is the supported comparison because awareness-context values can carry
informational flags. A verification failure should invalidate DPI-sensitive
geometry claims.

### Window DPI is not always monitor DPI

**DOCUMENTED.** [`GetDpiForWindow`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getdpiforwindow)
returns a value according to the target window's DPI awareness: `96` for a
DPI-unaware window, system DPI for a system-aware window, and the containing
monitor's DPI for a per-monitor-aware window. It returns `0` for an invalid
HWND. `GetWindowDpiAwarenessContext` returns the target window's context and is
not affected by the querying thread's awareness; see
[`GetWindowDpiAwarenessContext`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getwindowdpiawarenesscontext).

**R0 RECOMMENDATION.** Store the measurement as `window_dpi`, with its target
awareness when available. Do not label it universal `monitor_dpi`, and never
substitute `96` for failure. A normalized scale may be `window_dpi / 96.0` only
if its contract explicitly means the target window's effective DPI scale. It
must not be named or interpreted as physical monitor scale for all targets.

**R0 MODEL CONSTRAINT.** A core field named `display_scale` cannot safely be
populated from `GetDpiForWindow / 96.0` while claiming to represent monitor
scale: it would be `1.0` for every DPI-unaware target, even on a scaled monitor.
Define it as target-window effective scale, make it unavailable when the core
requires true display scale, or defer/rename it pending an approved monitor-DPI
source. Do not blur these two meanings merely to fill a required field.

### Monitor selection and work area

**DOCUMENTED.** [`MonitorFromWindow`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-monitorfromwindow)
chooses the monitor with the largest intersection with the window rectangle.
If there is no intersection, its result follows the caller's default flag. For
a minimized window, it uses the rectangle from before minimization.

**R0 RECOMMENDATION.** Use `MONITOR_DEFAULTTONEAREST` for a total best-effort
association, but record that policy. `MONITOR_DEFAULTTONULL` is useful in a
focused experiment that needs to distinguish off-monitor windows. Do not assume
the chosen monitor's DPI from `GetDpiForWindow` for a DPI-unaware or
system-aware target.

**DOCUMENTED.** Initialize `MONITORINFOEXW.cbSize`, then pass it to
[`GetMonitorInfoW`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getmonitorinfow).
[`MONITORINFO`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-monitorinfo)
defines `rcMonitor` and `rcWork` in virtual-screen coordinates; non-primary
monitor coordinates can be negative. `MONITORINFOEXW` adds a display device
name.

**R0 RECOMMENDATION.** Record monitor rectangle, work area, primary flag, and
device name where available. Treat the name/handle as current adapter metadata,
not a permanent cross-reboot display identity. Label both rectangles as
virtual-screen coordinates, preserve signed values, and verify their unit
congruence with both window rectangles in the mixed-DPI experiment matrix.

## Documented limits and design risks

1. **Asynchronous snapshot skew.** Out-of-context events are queued. A callback
   snapshot can describe a state later than `dwmsEventTime`; deferred enrichment
   can be later still.
2. **Reentrancy.** Sequential queue delivery does not remove callback
   reentrancy. Nested message processing can complete later events first unless
   guarded.
3. **No atomic census.** Enumeration and hook receipt cannot be represented as
   one OS snapshot.
4. **Ephemeral handles.** `IsWindow` cannot prevent destruction or handle
   recycling after a check.
5. **Event noise.** `EVENT_OBJECT_LOCATIONCHANGE` includes non-window accessible
   objects and child-window changes; identifier and ancestry filtering is
   mandatory.
6. **No documented pairing guarantee.** The event descriptions name starts and
   ends, but this review found no contract promising a perfectly balanced pair
   for every application or interruption. R0 must measure rather than assume.
7. **Visibility is not occlusion.** `IsWindowVisible` reports style state, not
   whether a user can see any pixels.
8. **Policy false positives.** Tool-window and app-window styles express window
   intent, but applications may use unusual combinations. Keep named reasons
   and raw facts.
9. **DWM availability/failure.** A failed extended-frame or cloak query is
   unknown, not “same as positioning bounds” or “not cloaked.”
10. **DPI semantic mismatch.** `GetWindowRect` is virtualized while DWM frame
    bounds are not DPI-adjusted. The PMv2 baseline is required before comparing
    them, and mixed-DPI results still need observation.
11. **Window DPI naming.** `GetDpiForWindow` can legitimately return `96` for a
    DPI-unaware target on a scaled monitor.
12. **Desktop/app-model coverage.** Process/thread-zero hooks cover the current
    desktop, and `EnumWindows` has a documented desktop-app scope on Windows 8+.
13. **Metadata permissions and races.** Process paths are optional; access may
    be denied or the process may exit.
14. **Backpressure.** Live resize can generate many geometry events. The answer
    is a bounded event-driven pipeline with explicit loss reporting, not
    high-frequency polling.

## Focused empirical questions for the R0 observer

Every item below is currently **NOT TESTED**.

### Event sequence and callback behavior

- Capture exact start/location/end sequences for mouse move, edge/corner resize,
  keyboard move/resize, maximize, restore, minimize, shell snap, and an
  application-originated geometry change.
- Record whether system move/size events consistently carry
  `OBJID_WINDOW/CHILDID_SELF`; do not promote this to a filter until observed.
- Determine whether starts and ends ever appear without a partner when a target
  closes, crashes, changes desktop, or the observer starts/stops mid-operation.
- Measure how many location events occur, whether duplicate rectangles occur,
  and whether a slow callback creates visible lag, backlog, or loss.
- Verify delivery from 32-bit and 64-bit targets, console/terminal windows,
  packaged applications, elevated targets, and hung targets without elevation
  or injection.
- Deliberately exercise the callback's reentrancy guard and queue-overflow
  diagnostic in a controlled observer-only test.

### Filtering

- Inventory rejected `not_visible`, `cloaked`, `child_or_nonroot`, and
  `tool_window_without_appwindow` rows by application class.
- Inspect whether legitimate user-facing palettes or utility windows are lost
  by the default tool-window rule.
- Correlate DWM cloak masks with shell/virtual-desktop state without claiming a
  cause beyond the documented bit value.
- Verify minimized windows remain observable and that their geometry is not
  accidentally used as current visible adjacency evidence.
- Test rapid close/recreate scenarios for PID mismatch and HWND reuse handling.

### Geometry, DPI, and monitor topology

- Compare `positioning_bounds` and `visible_frame_bounds` for Explorer,
  Notepad, Windows Terminal, a Chromium browser, VS Code, Excel, and Power BI
  Desktop where installed. Unavailable applications must be marked
  `NOT TESTED — environment unavailable`.
- Repeat normal, maximized, minimized, borderless/full-screen, and custom-frame
  states. Record DWM failures and rectangle deltas rather than generalizing.
- Use at least two monitors with different scaling, including a negative
  virtual-screen origin if available. Move a window across the boundary and log
  target awareness, `window_dpi`, both window rectangles, monitor rectangle,
  and work area at each event.
- Verify that a PMv2 observer sees positioning and DWM rectangles in a directly
  comparable unit space. If they are not congruent, stop geometry conclusions
  and preserve the evidence.
- Test a DPI-unaware, system-aware, and per-monitor-aware target to confirm the
  documented `GetDpiForWindow` distinction in actual logs.
- Test a straddling window and a minimized window to validate the documented
  `MonitorFromWindow` association behavior.

### Process metadata

- Record `QueryFullProcessImageNameW` success/failure for normal, elevated,
  protected/system-adjacent, short-lived, and packaged targets.
- Verify all access-denied and process-exit cases yield an otherwise usable
  snapshot with unavailable path, never an elevated retry.

## R0 research conclusion

The official API contracts are sufficient to implement a non-invasive R0
observer with a platform-neutral event model and deterministic geometry core.
They are not sufficient to claim real event sequences, pairing, filtering
quality, rectangle congruence, cross-DPI behavior, or application coverage.
Those remain explicitly `NOT TESTED` until the observer matrix is run.

The design remains inside R0: event-driven observation only, out of context,
no DLL injection, no high-frequency polling, and no third-party window control.

## Post-implementation evidence pointer

The `NOT TESTED` labels above describe the state at the official-documentation
gate. Subsequent R0 execution verified PMv2 startup, both hook registrations,
census, JSON serialization, and same-thread teardown; it also observed noisy
raw location-change receipts during an application launch. No manual
move/resize gesture was performed, so interactive start/location/end sequences,
pairing, mixed DPI, and multi-monitor behavior remain `NOT TESTED`. Exact counts
and application/status labels are recorded in
[`R0_EXECUTION_REPORT.md`](../reports/R0_EXECUTION_REPORT.md).
